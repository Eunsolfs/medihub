# 容量与冷数据归档（存储配额 / 冷数据归档）

医院素材是只增不减的：伤口照片、术中视频、培训课件会一直堆积，最终把服务器磁盘吃满。MediHub 用两层机制解决：

1. **存储配额**：给科室和全站设上限，超了就不让上传（413/507），把问题挡在门口；
2. **冷数据归档**：把「某个日期之前上传的」旧素材打包成分片 zip，推到 NAS/S3/本地目标，
   再从服务器删掉源文件，释放磁盘——归档包自带离线浏览页，随时能打开看。

本文只讲运维怎么规划容量、怎么设配额、怎么归档、归档后数据怎么找回来。

> **功能自检**：登录 `root` → **系统管理**，能看到 **存储** 标签页里的「存储配额」卡片、
> **归档** 标签页里的「冷数据归档」卡片，就说明当前版本包含这两个功能。
> 更早的 v1.0.0 没有它们，需要先升级（见 [UPGRADE.md](./UPGRADE.md)）。

## 1. 容量规划

### 1.1 先算清四笔账

| 账               | 怎么算                                                                                                                          | 落点                                               |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 素材本身         | 原始文件字节数之和（图片+视频+文档）                                                                                            | 服务器磁盘（本地/NAS 目标），或对象存储（S3 目标） |
| 备份             | **按素材总量 × 1** 预留（每日 `sqlite3 .backup` + `tar` 素材目录，见 [DEPLOY-1PANEL.md §12](./DEPLOY-1PANEL.md#12-备份与恢复)） | 同机另一个目录或远端                               |
| 归档临时空间     | 至少 **一个分片大小**（默认 200 MB）× 2（临时目录 + 读入内存）                                                                  | `/tmp` 所在分区 + 进程内存                         |
| 镜像备份（可选） | 只备数据库 ≈ 库文件大小；**勾选「同时复制素材文件」= 再一份素材总量**（见 §3.8）                                                | 另一块盘 / NAS / S3，**不要与站点同盘**            |

所以一条经验公式：

```
服务器磁盘 ≥ 素材总量（迟早会长到这个数） + 备份（等量） + 200 MB × 2 临时空间 + 系统与发行版（20 GiB）
```

镜像备份与归档包建议落在**别的存储**上，不占这条公式里的服务器磁盘。

短视频、术中录像增长最快：**1 分钟 1080p 手机视频约 100–200 MB**，一台手机的病例录像一年就能吃掉几十 GB。

### 1.2 配额定多少

| 层级     | 配置位置                              | 权限                                           | 建议                                                                  |
| -------- | ------------------------------------- | ---------------------------------------------- | --------------------------------------------------------------------- |
| 科室上限 | 系统管理 → 存储 → 存储配额 → 科室配额 | `root` 可设任意科室；`dept_admin` 只能设本科室 | 按「该科室一年素材增长 × 2」给，留出季度峰值余量                      |
| 全站上限 | 系统管理 → 存储 → 存储配额 → 全站上限 | **仅 `root`**                                  | = 磁盘可用空间 − 备份空间 − 512 MB 保留 − 其他用途（约磁盘的 40–50%） |

要点：

- 两个值都是**可空**的，留空 = 不单独限制（输入框 placeholder 就是「不限制」）；
- 上限只是「准入闸门」，**不会自动清理**任何东西，超了就得归档或扩容；
- 科室上限与全站上限是**与**关系：任一被突破都会拒传，所以别把科室上限配得比全站上限还高；
- `individual`（个人空间）也按科室算——注册时自动创建的个人空间就是一个 organization，
  它同样受全站上限约束（科室上限默认空，即不限，除非你给它设）。

### 1.3 为什么保留 512 MB

服务端在上传前会检查目标磁盘剩余，规则是：

```
剩余空间 − 本次文件大小 < 512 MB  →  拒绝（507）
```

这 512 MB 不是给素材留的，是给 **SQLite 与系统本身**留的：库文件在 WAL 模式下写入需要空间，
日志、临时文件、`soffice` 转换缓存也都要落盘。磁盘真的写满时 SQLite 会报
`disk I/O error`，症状比「上传失败」严重得多。所以这条检查**不可配置、不要绕过**。

### 1.4 S3 目标的两点不同

|                 | 本地 / NAS 目标            | S3 兼容目标                               |
| --------------- | -------------------------- | ----------------------------------------- |
| 磁盘剩余检查    | ✅ 做（`statfs` 目标路径） | ❌ **不做**（不占本机磁盘，无从检查）     |
| 科室 / 全站配额 | ✅ 受                      | ✅ **仍受**（配额在驱动检查之前就算完了） |
| 用量展示        | 会出现在「磁盘剩余」列表里 | 不出现                                    |

结论：想**彻底摆脱本机磁盘限制**，把默认存储目标换成一个 S3 目标（MinIO、OSS、Ceph 均可），
但**配额仍然生效**——需要同步把全站上限调大，否则 413 照旧。

## 2. 配额操作

### 2.1 界面路径

**系统管理 → 存储 → 存储配额**（`root` 与科室管理员可见；`member` / `individual` 进不了系统管理）。

卡片里三块内容：

| 区块     | 内容                                    |
| -------- | --------------------------------------- |
| 全站上限 | 已用 / 上限（仅 `root` 显示）           |
| 科室配额 | 每个科室一行：名称、已用 / 上限、输入框 |
| 磁盘剩余 | 每个本地/NAS 目标一行：路径、总量、剩余 |

右侧「刷新」按钮重新拉一遍用量。

### 2.2 GB ↔ 字节

界面上填 **GB**，接口与数据库存**字节**：

```
1 GB = 1024 × 1024 × 1024 = 1073741824 字节
上限（字节） = 输入的 GB × 1073741824，四舍五入到整数
显示值      = 已用字节 / 1073741824，保留 2 位小数
```

例：填 `500` → 库里 `536870912000`；改成 `0` → 上限变成 0 字节，等于**禁止任何上传**
（想取消限制请**清空**输入框，留空才是不限）。

### 2.3 什么时候生效

**保存即生效，不需要重启**：配额在每次上传时读取，改完立刻影响下一次上传。

### 2.4 统计口径

只有「**未删除、未归档**」的素材才计入用量，按 `asset.byte_size` 求和：

```sql
-- 等价于后台的统计口径（供手工核对）
select sum(byte_size) from asset
where deleted_at is null and archived_at is null;
```

由此有三个反直觉但重要的结论：

1. **软删除的素材立刻不计入**（进回收/删除后额度就回来了）；
2. **归档的素材立刻不计入**——**即使归档时没勾选「删除服务器源文件」**，额度也已经释放；
3. 文件在 S3 上也照样计入（配额看的是数据库里的字节数，不是磁盘）。

### 2.5 排查 413 / 507

上传失败时，前端弹出的就是服务端原样返回的消息，按消息定位：

| 状态码 | 消息关键字                                                       | 原因                                                         | 处理                                                                                                                                                   |
| ------ | ---------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 413    | `文件超过上限 N MB`                                              | **单文件**超过 `UPLOAD_MAX_BYTES`（默认 256 MB），与配额无关 | 改 `.env` 的 `UPLOAD_MAX_BYTES` 并重启；同时确认 Nginx 的 `client_max_body_size` 更大（见 [DEPLOY-1PANEL.md §9](./DEPLOY-1PANEL.md#9-nginx-反向代理)） |
| 413    | `科室存储空间不足：已用 X GB / 上限 Y GB`                        | 科室配额被打满                                               | 归档该科室旧素材，或调高科室上限                                                                                                                       |
| 413    | `全站存储空间不足：已用 X / 上限 Y`                              | 全站配额被打满                                               | 归档，或换更大磁盘/调高全站上限                                                                                                                        |
| 507    | `存储磁盘剩余空间不足：剩余 X GB，本次需要 Y MB，并需预留 512MB` | 目标磁盘物理空间不够                                         | 归档 + 勾选删除源文件，或换目标/加盘                                                                                                                   |
| 500    | `无法读取存储磁盘剩余空间，请检查挂载路径是否可访问`             | NAS 没挂载、路径写错、权限不足                               | 检查挂载点与目标配置（存储目标卡片里的 `rootPath`）                                                                                                    |

核对顺序（服务端就是这么判的）：**单文件上限 → 科室配额 → 全站配额 → 磁盘剩余**。
所以看到 413 先看消息内容是「单文件」还是「科室/全站」，别一上来就调配额。

手工核对用量与上限：

```bash
# 已用（全站）
sqlite3 /data/medihub/local.db \
  "select printf('%.2f GB', coalesce(sum(byte_size),0)/1073741824.0) from asset
   where deleted_at is null and archived_at is null;"

# 科室上限（字节 → GB）
sqlite3 /data/medihub/local.db \
  "select name, printf('%.2f GB', quota_bytes/1073741824.0) from organization where quota_bytes is not null;"

# 全站上限（存在 app_setting 表里）
sqlite3 /data/medihub/local.db \
  "select key, printf('%.2f GB', value/1073741824.0) from app_setting where key='storage.globalQuotaBytes';"

# 目标磁盘剩余
df -h /data/medihub/storage
```

## 3. 归档操作

### 3.1 什么时候归档

经验阈值（按科室的实际增长调整）：

| 信号                                 | 动作                                                 |
| ------------------------------------ | ---------------------------------------------------- |
| 磁盘剩余 < 30%，或上传开始零星报 507 | 归档 2 年前的素材                                    |
| 某科室配额长期 > 80%                 | 归档该科室 1 年半以前的素材（dept_admin 可自己做）   |
| 患者结案/随访结束后 6–12 个月        | 该患者相关素材可以归档                               |
| 有法规/院规的留存期                  | **先满足留存期**，再归档（归档不等于删除，仍可下载） |

推荐节奏：**每季度一次**，固定归档「截止日期 = 今天 − 2 年」。归档是增量安全的——
已归档的素材会自动被排除，重复执行不会重复打包。

### 3.2 选存储目标

**系统管理 → 归档 → 新建归档 → 存储目标**。

| 目标             | 适合                                     | 注意                                            |
| ---------------- | ---------------------------------------- | ----------------------------------------------- |
| **S3 / MinIO**   | 最推荐：释放本地盘最彻底，且不占本机空间 | 出网带宽决定打包速度；凭证错会整个任务失败      |
| **NAS 挂载路径** | 院内已有 NAS、数据不出院                 | 受挂载稳定性影响；`statfs` 不可读会导致上传被拒 |
| **本地另一块盘** | 最小改动                                 | 不释放整机空间，只换了盘符/分区                 |

不选的话用「当前默认存储目标」。

> 归档包写入的是**存储目标**（和素材同一个驱动），路径固定为 `archive/<jobId>/chunk-00N.zip`。
> 换目标只影响**新的**归档任务，历史分片仍从各自的目标读取。

### 3.3 四个必填/可选项

| 字段                   | 默认        | 说明                                                                              |
| ---------------------- | ----------- | --------------------------------------------------------------------------------- |
| 归档科室               | 当前科室    | 仅 `root` 显示选择器；`dept_admin` 固定本科室                                     |
| 截止日期               | 今天 − 2 年 | 只归档**上传时间早于该日期**的素材（`created_at`，不是拍摄时间）                  |
| 分片大小               | 200 MB      | 可选 50 MB / 100 MB / 200 MB / 512 MB / 1 GB / 2 GB / 4 GB；接口允许 50 MB – 8 GB |
| 存储目标               | 默认目标    | 见 §3.2                                                                           |
| 归档后删除服务器源文件 | **勾选**    | 勾了才真正释放磁盘；不勾只是打包一份副本                                          |

**关于「截止日期」的时区细节**：日期选择器传的是 `YYYY-MM-DD`，服务端按 **UTC 零点**解析，
换算到北京时间就是**当天 08:00**。也就是说选 `2024-10-01`，实际归档的是
「北京时间 2024-10-01 08:00 之前上传的」素材。想稳妥就把日期往前多选一天。

### 3.4 分片大小怎么选

分片是下载与校验的最小单位，也是**内存与临时盘的峰值**，权衡如下：

| 片大小             | 优点                                       | 缺点                                 | 适合                       |
| ------------------ | ------------------------------------------ | ------------------------------------ | -------------------------- |
| 50 / 100 / 200 MB  | 峰值内存与 `/tmp` 占用小；单片失败重试便宜 | 片数多，手工逐片下载慢               | 小服务器（2C4G）、弱网出网 |
| **200 MB（默认）** | 内存 / 片数较均衡                          | 大素材量时片数仍然可观               | 绝大多数科室               |
| 512 MB / 1 GB      | 片数适中                                   | 需要 0.5–1 GB 的 `/tmp` 与内存余量   | 4C8G 以上、内网千兆        |
| 2 GB / 4 GB        | 片数最少，拷贝到移动硬盘方便               | 单片下载慢、失败重来代价大；很吃内存 | 大文件为主、专线环境       |

关键约束（来自实现）：

- 每片 zip 先写到 **系统临时目录**（`$TMPDIR`/`/tmp`），完成后才上传到目标，
  所以 `/tmp` 所在分区必须能放下**一整片**；
- 单片在内存里读成完整 Buffer 再写存储，所以**分片大小 ≈ 峰值内存增量**；
- **单个素材大于分片大小时，它独占一片**（片会超过设定值）——所以有 3 GB 的术中视频，
  那片就是 3 GB，别把分片设得比最大的单个文件还小太多；
- 片数 = 素材总体积 / 分片大小（大致），片数越多，下载与校验的人工成本越高。

建议：

| 你的服务器              | 建议分片           |
| ----------------------- | ------------------ |
| 2C4G / `/tmp` 只有 2 GB | 50–200 MB          |
| 4C8G，常规混合素材      | **200 MB（默认）** |
| 8C16G，4K 视频为主      | 512 MB – 1 GB      |
| 需要拷进移动硬盘交付    | 1–2 GB（片少好拷） |

### 3.5 执行过程与耗时

点「创建归档任务」后，任务在**后台**跑，界面列表自动刷新（有任务处于「打包中」时轮询）。
状态依次是：

| 状态                           | 含义                             |
| ------------------------------ | -------------------------------- |
| `running`（界面「打包中」）    | 正在读素材、写 zip、传目标       |
| `ready`（界面「已完成」）      | 全部分片就绪，素材已标记归档     |
| `failed`（界面「失败」+ 原因） | 中途失败，**素材不会被标记归档** |

注意执行顺序（决定了失败时的安全性）：

```
读取素材（最多 5000 条）
  → 逐片打包并上传
  → 全部成功后：标记 asset.archived_at / archive_id
  → 若勾选了删源：逐个删除源文件（单个删不掉不影响整体）
  → 写入 chunk_count / chunks / completed_at，状态置 ready
```

**失败发生在「标记」之前的话，什么都没改**，直接重试即可（但已上传的分片会留在存储里，成为孤儿，需要时手工清）。

耗时经验值（千兆内网、S3 同城）：

| 素材量 | 打包+上传  |
| ------ | ---------- |
| 10 GB  | 8–20 分钟  |
| 100 GB | 1.5–4 小时 |
| 500 GB | 一晚上     |

CPU 不是瓶颈（zip 压缩级别 6），**读源 + 写目标 + 内存拷贝**才是。

### 3.6 失败怎么重试

1. 在列表里看失败原因（列表行的 `error`）；
2. 常见原因见 §8.4；
3. 修好后**新建一个同样的任务**即可：已成功归档的素材不会被重复打包；
4. 清理孤儿分片（可选，见 §8.3）。

### 3.7 定时归档计划

手工归档适合「想起来了才做」，但容量管理应该是常态。**定时归档计划**让服务端按固定节奏自动
创建归档任务（§3.1 的「每季度归档 2 年前素材」可以直接配成一条计划）。

**界面：系统管理 → 归档 → 归档计划 → 新建计划**（`root` 与科室管理员；`root` 可指定科室）。
卡片标题就是「归档计划」，每行一个任务，右侧有启用开关、编辑、删除。

#### 3.7.1 字段

| 字段               | 默认         | 说明                                                           |
| ------------------ | ------------ | -------------------------------------------------------------- |
| 计划名称/所属科室  | 当前科室     | `root` 需先在顶部选科室，或在下拉里指定                        |
| 启用               | 开           | 关掉即停止触发，历史任务不受影响                               |
| 频率               | 每月         | `每天` / `每周` / `每月`                                       |
| 执行时刻（整点）   | 03:00        | 按**服务器本地时区**的整点，0–23。避开备份与门诊高峰           |
| 星期几             | 周一         | 仅「每周」使用，1=周一 … 7=周日                                |
| 每月几号           | 1 号         | 仅「每月」使用，**1–28**（避开 29/30/31 这类月末不存在的日期） |
| 归档多少天前的素材 | 730 天       | 等价于手工归档里「截止日期 = 今天 − N 天」                     |
| 分片大小           | 200 MB       | 同 §3.4，可选项一致                                            |
| 存储目标           | 当前默认目标 | **强烈建议 NAS / S3**，见下方「本地磁盘 200 MB 规则」          |
| 归档后删除源文件   | 开           | 自动任务默认真删源，否则起不到释放磁盘的作用                   |

计划行会显示 `上次运行`、`下次运行`（`next_run_at`）、`上次任务 id`、`最近错误`（`last_error`）。

#### 3.7.2 什么时候触发

- 服务端**每分钟**扫描一次（进程内定时器，启动后 5 秒先跑一次），取 `enabled = true` 且
  `next_run_at <= 现在` 的计划，每轮最多 5 条；
- 到点后按参数创建一条**普通归档任务**（和手工创建走同一套流程与状态机，见 §3.5），
  成功后把 `last_run_at` / `last_job_id` 写回计划并清空 `last_error`；
- 然后重算 `next_run_at`：从「当前时刻」往后找第一个满足「频率 + 整点」的时间点——
  今天的整点还没到就是今天，已经过了才顺延（`每天` → 明天同整点；`每周` → 下周同星期几；
  `每月` → 下月同一天，日期上限 28，所以不会出现「2 月没有 30 号」的问题）；
- 时间都按**服务器本地时区**算，部署时务必设对（[DEPLOY-1PANEL.md §15](./DEPLOY-1PANEL.md#15-故障排查) 的时区一节）。

> **多实例部署注意**：调度器跑在进程内，多副本会重复触发。本项目默认单机单进程，无需处理；
> 若将来上多实例，只在一个实例启用它（或在编排里只给一个副本开）。

#### 3.7.3 本地磁盘的 200 MB 规则（很重要）

当归档目标是**本地磁盘**（存储目标的驱动是 `local`）时，计划在真正执行前会先估算
「本次待归档素材的总体积」，**只有小于 200 MB 才允许执行**；达到或超过就**不执行**，
把原因写进 `last_error` 并跳过这一轮，等下一个周期。

跳过的错误文案长这样（可以直接拿这段去搜运维记录）：

```text
预计归档 1234.5MB，超过本地目标 200MB 限制；请改用 NAS/S3
```

这条规则是防止自动任务把服务器自己的盘写满（归档包和站点在同一块盘上时，边打包边写等于
「左口袋挪右口袋」，没有收益还有炸盘风险）。所以：

- 只有 **`local` 驱动**受这条限制；**NAS 挂载路径（`nas` 驱动）与 S3 都不受限**——
  它们本来就是「别的盘」，值得作为计划的归档目标；
- 如果你只有本地盘，那定时计划只能应付小批量；大批量仍然要手工归档 + 勾选删源（或先加盘/上 NAS/S3）；
- 看到计划 `last_error` 里是上面这句，不是故障，是设计如此。

#### 3.7.4 失败会怎样

| 情况                           | 行为                                                                        |
| ------------------------------ | --------------------------------------------------------------------------- |
| 到点时没有可归档的素材         | 本轮跳过，`last_error` 记录「这个时间点之前没有可归档的素材」；下个周期继续 |
| 目标是 `local` 且体积 ≥ 200 MB | 本轮跳过，`last_error` 记录「超过本地目标 200MB 限制」；下个周期继续        |
| 目标不可写 / 凭证失效 / 磁盘满 | 本轮跳过，`last_error` 记录；**不会立即重试**，等下一个周期                 |
| 计划本身被关掉                 | 不再触发；已创建的任务照常跑完                                              |

计划**没有「失败立即重试」**：靠的是「下个周期再来一次」+ 你在列表里看到的 `last_error`。
想马上补一次，按相同参数手工「新建归档」跑一次即可（已归档的素材会被自动排除，不会重复打包）。

> 每轮最多处理 **5 条**到期计划（后端限制）。如果同一分钟有大批计划同时到期，它们会在接下来
> 的几分钟里陆续被处理——不丢任务，只是错峰执行。

#### 3.7.5 停用与删除

- **临时停用**：计划行内的「启用」开关关掉即可（`enabled = false`），历史任务与归档包不受影响；
- **删除计划**：删除后不再触发，同样不影响历史任务；
- 停用/删除计划**不会删除**已经归档的素材或分片，也不会把额度退回来（归档本来就已释放额度）。

命令行核对（排查时用）：

```bash
# 启用中的计划与下次触发时间
sqlite3 /data/medihub/local.db \
  "select id, frequency, hour, weekday, day_of_month, before_days,
          printf('%.0f MB', chunk_bytes/1048576.0) as chunk,
          datetime(next_run_at/1000,'unixepoch','localtime') as next_run,
          datetime(last_run_at/1000,'unixepoch','localtime') as last_run,
          last_error
   from archive_schedule where enabled=1 order by next_run_at;"

# 关掉的计划
sqlite3 /data/medihub/local.db "select id, last_error from archive_schedule where enabled=0;"
```

### 3.8 镜像备份（仅 root）

归档解决「旧素材占地方」，镜像备份解决**「数据万一没了怎么办」**：把**整个数据库**（可选连同
**全部素材**）复制到另一个存储目标，形成一份与站点数据无关的冷副本。

**界面：系统管理 → 存储 → 镜像备份 → 立即镜像**（卡片在「存储」标签页底部，仅 `root` 渲染；
接口同样只有 root 能调，不是仅隐藏界面）。

卡片上有三样东西：目标下拉（默认「使用默认存储目标」）、「同时复制素材文件」勾选框（默认**不勾**）、
以及「立即镜像」按钮；下面是最近 10 条任务，每条标注「仅数据库快照 / 含素材文件」、大小、素材数与错误。

#### 3.8.1 它做了什么

1. 对 SQLite 做 **一致性快照**（`VACUUM INTO`）——不是直接拷 `.db` 文件，因此不会拿到
   「写到一半 + 一份 `-wal`」的撕裂状态；
2. 快照写到目标存储的 `mirror/<jobId>/medihub.sqlite`；
3. 勾选「**同时复制素材文件**」时，再把**所有未删除的素材**（含已归档的）复制到
   `mirror/<jobId>/files/<素材id>-<原文件名>`（体积 = 素材总量，可能非常大）；
4. 写一份 `manifest.json`（schema `medihub.mirror/v1`）：记录 `jobId`、创建时间、
   `includeAssets`、实际复制的素材数与字节数、快照的 `checksum`（数据库快照的 SHA-256）；
5. 任务状态与错误进列表（最近 10 条）。

任务列表会显示：状态（`pending` / `running` / `ready` / `failed`）、大小、素材数、错误原因。
**只有 `root` 能看、能触发**（接口层按 root 校验，不是仅隐藏界面）。

> 单个素材读不到（源文件已被删、目标不可达）不会让整个镜像失败：它会被跳过，
> `manifest.json` 里的 `assetCount` 反映的是**实际复制成功**的数量。

#### 3.8.2 选目标

| 目标                   | 说明                                                        |
| ---------------------- | ----------------------------------------------------------- |
| **S3 / MinIO（推荐）** | 天然异地/多副本，最适合「灾难恢复」这一层；素材量大也可接受 |
| **NAS**                | 院内、可控；注意别和站点共用同一块物理盘                    |
| **本地另一块盘**       | 只能防「误删/误操作」，防不了整机损坏                       |

关键：**镜像目标不要与站点数据、也不要与归档包放在同一块物理盘上**，否则一次磁盘故障全没。

#### 3.8.3 占用空间

| 内容               | 体积                                                                         |
| ------------------ | ---------------------------------------------------------------------------- |
| 数据库快照         | ≈ `local.db` 大小（几 MB – 几百 MB）；`VACUUM INTO` 会顺带整理碎片，通常略小 |
| 素材副本（勾选时） | = 全站在用素材总量（几十 GB – TB 级），**每次备份都是全量**                  |
| manifest           | 可忽略                                                                       |

所以：只勾「数据库」时几乎不占地方，适合**每天一次**；勾「素材」时建议**每周/每月一次**，
并给目标留出至少 **2 × 素材总量**（新旧两份同时在）。

每次备份都是一个独立目录 `mirror/<jobId>/`，**不会自动删除旧备份**——清理策略见 §8.3。

#### 3.8.4 恢复方式

镜像包里的 `medihub.sqlite` 就是一个标准 SQLite 文件，恢复时把它放回 `DATABASE_URL` 指的路径
（默认 `apps/server/local.db`）即可：

```bash
# 1) 停服务
sudo systemctl stop medihub

# 2) 备份现状（保命）
sudo -u www -H cp /data/medihub/local.db /data/medihub/local.db.before-restore.$(date +%s)

# 3) 从镜像目标取回快照（本地/NAS 目标直接 cp；S3 用 rclone/aws-cli/面板下载）
sudo -u www -H cp /mnt/nas/medihub/mirror/<jobId>/medihub.sqlite /data/medihub/local.db

# 4) 清掉旧的 WAL，避免与新库混用
sudo rm -f /data/medihub/local.db-wal /data/medihub/local.db-shm

# 5) 起服务并验证
sudo systemctl start medihub
curl -fsS http://127.0.0.1:3000/api/health      # {"status":"ok","version":"…"}
```

要点：

- **先停服再换库**，运行中替换会留下不一致的 `-wal`；
- 恢复的是**数据库**。素材文件仍在它们各自的存储目标里（归档过的除外，归档时删了源）；
- 若镜像时**勾选了「同时复制素材文件」**，镜像里是扁平目录 `mirror/<jobId>/files/<素材id>-<原文件名>`，
  **不是**原来的 `storage/<组织>/<年月>/<hash>.<ext>` 结构。要真正恢复可用，需要按数据库里的
  `storage_key` 把文件放回对应存储目标的位置（批量恢复请让维护者写脚本，别手工一个个来）；
- `.env`、`storage/` 下的 `.office-cache`、`.updates/` **不在镜像范围内**，需要另外备份。

恢复前先核对快照完整性（`manifest.json` 里有快照的 SHA-256）：

```bash
cd /path/to/mirror/<jobId>
# 计算快照的 sha256，与 manifest 里的 checksum 对比
sha256sum medihub.sqlite
python3 -c "import json;print(json.load(open('manifest.json'))['checksum'])"

# 快照能打开、表在（覆盖式替换前先验证）
sqlite3 medihub.sqlite "select count(*) from asset; select count(*) from archive_job;"
```

#### 3.8.5 与「归档」的区别

|                  | 冷数据归档（§3.x）                                    | 镜像备份（本节）                                                |
| ---------------- | ----------------------------------------------------- | --------------------------------------------------------------- |
| 目的             | 释放磁盘 / 下线旧数据                                 | 灾难恢复                                                        |
| 范围             | 按截止日期挑出的**旧素材**                            | **整个数据库**（可选全部素材）                                  |
| 频率             | 每季度 / 每月计划                                     | 每天（库）/ 每周（库+素材）                                     |
| 对站点的影响     | 素材变成「不可预览」，仍检索得到                      | **无影响**，纯副本                                              |
| 是否占用配额     | 归档后释放额度                                        | 不影响（库里的字节数没变）                                      |
| 能否单独取回一条 | 能（解压分片后单文件恢复上传）                        | 能（从快照里查/导出，或整库恢复）                               |
| 能不能省磁盘     | 能                                                    | **不能**，反而多占一份                                          |
| 产物             | `archive/<jobId>/chunk-00N.zip`（自带 `viewer.html`） | `mirror/<jobId>/medihub.sqlite` + `manifest.json`（+ `files/`） |
| 谁能用           | `root` / `dept_admin`                                 | **仅 `root`**                                                   |

一句话：**归档是「搬家」，镜像是「留底」**。两个都要有——归档让系统能长期跑下去，
镜像让误删/损坏/勒索软件之后还能救回来。

## 4. 归档后数据怎么查

### 4.1 站点里还在不在

**还在。** 归档**不删除数据库记录**，素材行、时间线、资料库里的条目都保持原样；
只有「能不能打开原文件」会变：

| 归档时是否删源     | 站点里的表现                                                                                  |
| ------------------ | --------------------------------------------------------------------------------------------- |
| 勾选了删除（默认） | 素材仍列出，但打开时 `GET /api/files/<id>` 返回 **410 `文件已从存储中移除`**，预览/下载不可用 |
| 没勾选             | 完全正常，仍可预览下载（但额度已释放，注意别误以为没归档成功）                                |

> 目前前端**没有「已归档」徽标**（归档面板文案里提到、界面未实现）。要判断某条素材是否
> 已归档，看下面两个字段，或直接看它还能不能打开。

```bash
# 某科室已归档的素材（含所属归档任务）
sqlite3 /data/medihub/local.db \
  "select id, original_name, byte_size, datetime(archived_at/1000,'unixepoch','localtime'), archive_id
   from asset where archived_at is not null order by archived_at desc limit 20;"
```

### 4.2 取回原始内容（标准流程）

1. **系统管理 → 归档**，找到对应任务（可按「截止」日期辨认）；
2. **完成**状态的任务，在行内点「下载第 N 片」，把需要的分片全部下载下来
   （文件名形如 `medihub-archive-xxxxxxxx-001.zip`）；
3. 解压：

   ```bash
   mkdir -p ~/medihub-archive && cd ~/medihub-archive
   unzip -o /path/to/medihub-archive-xxxxxxxx-001.zip
   unzip -o /path/to/medihub-archive-xxxxxxxx-002.zip     # 多片解压到同一目录即可合并
   ```

4. **直接双击 `viewer.html`**，浏览器会打开一个离线浏览页：图片/视频就地预览、每项都有
   「下载原文件」链接。断网也能用（页面没有任何外链资源）。

> 多片之间是同目录合并的关系：每片都有自己的 `manifest.json` / `README.md` / `viewer.html`，
> 覆盖式解压会以后解的那片为准；`files/` 里的文件名带序号前缀（`0001-` 起），不会互相覆盖。
> 想看**全部**素材的清单，请以各片的 `manifest.json` 为准，或按 §4.3 合并。

### 4.3 `manifest.json` 里有什么

每片一个 `manifest.json`（schema `medihub.archive/v1`），是二次开发与检索的入口：

```json
{
  "schema": "medihub.archive/v1",
  "archive": {
    "chunkIndex": 0,
    "createdAt": "2026-10-25T01:12:33.000Z",
    "deleteSource": true,
    "jobId": "0f3c…",
    "organization": {
      "code": "plastic-surgery",
      "id": "…",
      "name": "整形外科"
    },
    "requester": { "email": "root@…", "id": "…", "name": "系统管理员" },
    "targetName": "NAS 归档"
  },
  "assets": [
    {
      "admissionId": "…",
      "archivedAt": "2026-10-25T01:12:33.000Z",
      "byteSize": 2411724,
      "capturedAt": "2024-03-02T02:10:00.000Z",
      "createdAt": "2024-03-05T07:20:11.000Z",
      "description": "术前记录",
      "id": "…",
      "kind": "image",
      "mimeType": "image/png",
      "name": "术前-1-1.png",
      "patientId": "…",
      "relativePath": "files/0001-术前-1-1.png",
      "stage": "preop",
      "tags": ["瘢痕", "preop"]
    }
  ]
}
```

要点：

- `assets[].relativePath` 就是包内路径，与 `files/` 下真实文件一一对应；
- `assets[].byteSize` 可用于解压后核对完整性；
- `archive.chunkIndex` 从 0 开始（与下载 URL 的 `<index>` 一致，见 §7）；
- **manifest 里没有 checksum**：原库的 `checksum` 字段没有进包，逐字节校验需要另行记录。

常用检索：

```bash
# 把某个患者的所有素材路径都列出来（先解压所有片到同一目录）
jq -r '.assets[] | select(.patientId=="<患者id>") | .relativePath' */manifest.json

# 只要视频清单
jq -r '.assets[] | select(.kind=="video") | "\(.byteSize)  \(.relativePath)"' */manifest.json | sort -nr
```

### 4.4 只看某一类

- 只想看图片/视频：直接开 `viewer.html`，按视觉找；
- 想按患者/分期查：用 §4.3 的 `jq`；
- 想还原「原始时间线」：`manifest.json` 有 `capturedAt` / `createdAt` / `stage`，
  可按 `capturedAt` 排序后建一个自己的索引页。

## 5. 为什么不推荐直接「导入」回站点

归档包是**离线快照**，不是「可回挂的存储」。把它再导入站点，代价与风险都比想象大：

| 代价           | 说明                                                                                  |
| -------------- | ------------------------------------------------------------------------------------- |
| 磁盘又满了     | 导入 = 把字节搬回服务器磁盘，配额与 512 MB 检查都会重新生效                           |
| 解析与写库成本 | 需要新写一个导入器：读 manifest → 逐文件上传 → 建 asset 行（新 id，可能与旧 id 冲突） |
| 关系丢失       | 原有的 `admission_id` / `patient_id` / 时间线顺序需要重建，导错会污染时间线           |
| 重复数据       | 同一条素材变成两条记录，之后导出/统计都会重复计数                                     |

### 5.1 替代方案 A：只读挂载归档盘（推荐）

如果归档目标就是院内 NAS，**不需要导入**：把 NAS 挂到需要的机器上，用 `viewer.html` 或文件管理器
直接浏览。网站只负责「在线活数据」，归档盘负责「历史只读」。

```bash
# 例：把归档目录挂到工作站只读位置（macOS / Linux 挂载 NFS 或 SMB 均可）
sudo mount -t nfs 10.0.0.10:/export/medihub-archive /mnt/medihub-archive -o ro
find /mnt/medihub-archive -name viewer.html -maxdepth 3 | head
```

### 5.2 替代方案 B：按需恢复单个文件

只要某几个文件（比如一张术前照片），别整包导入：

1. 按 §4.2 解压，找到 `files/0001-xxx.png`；
2. 走正常业务路径**重新上传**到网站（患者详情 → 上传 / 资料库 → 上传），
   它会得到新的素材 id，并正常计入配额；
3. 更好的做法是只把**引用留在归档里**，用「归档批次 + 文件名」在院内文档里指路。

### 5.3 替代方案 C（谨慎）：直接改回去

有人会想「把 `storage_key` 改回原来的路径、清掉 `archived_at`」——技术上可行，但**必须**
先备份数据库，并且只在「归档时没删源文件」或「已把分片解压回原目录」时才有意义：

```bash
# 先停服并备份！
sudo systemctl stop medihub
sudo -u www -H sqlite3 /data/medihub/local.db ".backup '/www/backup/medihub/before-unarchive.db'"

# 危险操作示例：把某条素材「取消归档」（仅在文件确实回到 storage_key 指向的位置时）
# .mode box
# select id, storage_key, archive_id, datetime(archived_at/1000,'unixepoch','localtime')
#   from asset where id='<素材id>';
# update asset set archived_at=null, archive_id=null where id='<素材id>';

sudo systemctl start medihub
```

风险提示：这条路径**绕过了所有配额与完整性校验**，也没有审计记录；一旦 `storage_key` 指错，
用户打开会看到 410 或张冠李戴的文件。**能不用就不用**，要批量恢复请让维护者写正式脚本 + 加审计。

## 6. 桌面端查看方案

归档包的 `viewer.html` 是**自包含**的：样式内联、预览用相对路径、无 CDN、无脚本依赖，
所以 `file://` 直接打开即可。围绕这一点有三种方案：

| 方案                          | 成本            | 体验                                                             | 适合                           |
| ----------------------------- | --------------- | ---------------------------------------------------------------- | ------------------------------ |
| **a. 浏览器直接打开**         | 0               | 网格浏览、图片/视频预览、逐个下载                                | 临时查阅、审计抽检             |
| **b. Tauri / Electron 套壳**  | 低（半天~2 天） | 独立窗口、可固定「最近打开的归档目录」、可加大文件缓存与批量导出 | 科室固定工位、需要长期查阅历史 |
| **c. 只读导入模式（改代码）** | 高（1–2 周）    | 归档包能像资料库一样浏览、按患者/时间检索                        | 归档量很大、检索需求强         |

### 6.1 a：直接打开（推荐先这么用）

```bash
# 解压到固定位置
mkdir -p /data/archive-viewer/2026-Q4 && cd /data/archive-viewer/2026-Q4
unzip -o /path/to/medihub-archive-xxxxxxxx-001.zip
xdg-open viewer.html          # macOS: open viewer.html；Windows: start viewer.html
```

发给同事时只需把**解压后的整个目录**（或 zip 包）拷过去，对方双击 `viewer.html` 即可，
不需要装任何东西。注意 `viewer.html` 依赖同目录的 `files/`，别单独发这一个文件。

### 6.2 b：套一层桌面壳（Tauri）

本项目可以用 VibeStart 生成一个 Tauri 桌面壳，把「打开归档目录 → 渲染 viewer.html」包起来：

```bash
# 仅示意：在空的工程目录里生成 Tauri 壳，按向导选 desktop=tauri
npx vibestart-cli create my-archive-viewer
```

壳里要做的事很少：

1. 一个「选择归档目录」按钮（原生的目录选择器）；
2. 用 WebView 打开 `<目录>/viewer.html`（或把目录注册成自定义协议 / 本地静态服务）；
3. 记住上次打开的目录，下次启动直达。

好处是**完全离线**、可加只读保护（禁用右键/另存为按需），适合放在科室公用电脑上；
代价是多一个需要分发的安装包（Windows 上还要考虑代码签名）。

### 6.3 c：只读导入模式（后续可选）

思路：给站点加一个「挂载归档包（只读）」能力——把归档目录登记为一个 `archive_mount`，
浏览时直接读包内文件、不写 asset 表、不计配额、不参与导出。成本在于：

- 需要新的只读存储驱动（能读 zip 内偏移，或解压后当普通目录读）；
- 页面要区分「活数据」与「归档数据」的权限与 UI；
- 检索要单独建索引（manifest 里有元数据，可以喂给同一套筛选）。

在这条路走通之前，**别用「导入」来凑**，见 §5。

## 7. 大文件与分片下载

### 7.1 下载地址与编号

| 项             | 值                                                                                             |
| -------------- | ---------------------------------------------------------------------------------------------- |
| 接口           | `GET /api/archive/<jobId>/<index>`                                                             |
| `index`        | **从 0 开始**（第 1 片是 `/0`，第 2 片是 `/1`）                                                |
| 保存时的文件名 | `medihub-archive-<jobId 前 8 位>-<序号 3 位>.zip`，如 `medihub-archive-0f3c9a12-001.zip`       |
| 权限           | **仅 `root` 与 `dept_admin`**；`dept_admin` 只能下本科室的（跨科室返回 404，非管理员返回 403） |

命令行下载（绕过浏览器，便于脚本化）：

```bash
# 先登录拿 cookie（在浏览器 F12 → Network 里复制 Cookie 头，或用下面的 curl 登录）
curl -fsS -c cookies.txt -X POST https://medihub.example.com/api/auth/sign-in/email \
  -H 'Content-Type: application/json' \
  -d '{"email":"root@example.com","password":"<密码>"}'

JOB=0f3c9a12-1111-2222-3333-444455556666
curl -fL -b cookies.txt -o chunk-001.zip \
  "https://medihub.example.com/api/archive/$JOB/0"
```

### 7.2 断点续传 / 失败重试

分片接口支持 `Range`，返回 `206` 与 `Content-Range`，因此可以续传：

```bash
# 已下了 300MB 断了：从这里接着下
curl -fL -b cookies.txt -C - -o chunk-001.zip \
  "https://medihub.example.com/api/archive/$JOB/0"

# 校验服务端支持 Range
curl -sI -b cookies.txt "https://medihub.example.com/api/archive/$JOB/0" | grep -i accept-ranges
# 期望：accept-ranges: bytes
```

常见返回码：

| 码        | 含义                                   | 处理                       |
| --------- | -------------------------------------- | -------------------------- |
| 200 / 206 | 正常 / 部分内容                        | —                          |
| 401       | 没登录或 cookie 过期                   | 重新登录                   |
| 403       | 当前账号不是 `root` / `dept_admin`     | 找管理员下载               |
| 404       | `jobId` 不存在、分片序号越界，或跨科室 | 核对任务 id 与分片数       |
| 410       | 存储目标被删，或分片对象被移走         | 找运维确认存储目标是否还在 |
| 416       | `Range` 越界                           | 去掉 `-C -` 重新整片下载   |

### 7.3 解压前先校验

服务端不提供分片校验和，但你可以用两条低成本的自检：

```bash
# 1) zip 结构完整性（能读目录即结构没坏）
unzip -t chunk-001.zip | tail -3

# 2) 逐个文件大小与 manifest 比对（bash + jq）
unzip -q chunk-001.zip -d /tmp/chk
jq -r '.assets[] | "\(.byteSize)\t\(.relativePath)"' /tmp/chk/manifest.json |
while IFS=$'\t' read -r size path; do
  actual=$(stat -c%s "/tmp/chk/$path" 2>/dev/null || echo missing)
  [ "$actual" = "$size" ] || echo "MISMATCH $path (期望 $size, 实际 $actual)"
done
echo "校验完成"
```

浏览器下载大文件更容易中断（尤其经过反代）。建议：**分片别设太大**（§3.4）、
下载时不要并发太多片、断点续传用 `curl -C -` 而不是反复点浏览器重下。

## 8. 运维

### 8.1 备份

归档会改变两类数据，都要进备份：

| 对象                             | 为什么                                                                                                    | 怎么做                                                                             |
| -------------------------------- | --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `local.db`（含 `-wal` / `-shm`） | `archive_job` 表存着每个分片的 `key` / `index` / `size`；**没有这张表，分片包就是一堆不知道属于谁的 zip** | 沿用 [DEPLOY-1PANEL.md §12](./DEPLOY-1PANEL.md#12-备份与恢复) 的 `sqlite3 .backup` |
| 归档包本身                       | 分片通常已在 NAS/S3，本身有冗余；但若归档目标是「本机另一块盘」，它和站点在同一台机器上                   | 对归档目标目录也做一份异地副本                                                     |

关键一条：**数据库与归档包必须成对可恢复**。只留 zip 没有数据库，就不知道每个包覆盖了哪些
素材、属于哪个科室、对应哪个分片序号。

### 8.2 归档包校验

建议每季度抽一个任务做完整性检查：

```bash
# 从 NAS 侧看某个任务的分片是否齐全（数量 = 列表里的「N 个分片」）
ls -lh /mnt/nas/medihub/archive/<jobId>/
unzip -t /mnt/nas/medihub/archive/<jobId>/chunk-001.zip | tail -1

# 库里记录的分片清单
sqlite3 /data/medihub/local.db \
  "select chunk_count, byte_size, asset_count, status from archive_job where id='<jobId>';"
sqlite3 /data/medihub/local.db "select chunks from archive_job where id='<jobId>';"
```

### 8.3 清理策略

| 对象                  | 建议                                                                                                                                                 |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 本地 staging/临时文件 | 服务端自己会清理（`/tmp/medihub-archive-*`）；异常退出可能残留，可定期 `find /tmp -maxdepth 1 -name 'medihub-archive-*' -mtime +7 -exec rm -rf {} +` |
| 失败任务的孤儿分片    | 失败时已上传的分片不会自动删。确认不再重试后，手工删 `archive/<jobId>/` 目录（库里的任务记录保留，下载会返回 410）                                   |
| 老归档包              | 按院规留存期处理。**没有「删除归档任务」接口**，清理只能在存储侧做，并在运维记录里写清删了哪个 jobId                                                 |
| 站点里的素材行        | 归档不删行。真要清理请走业务侧的删除（软删除），别直接 `delete from asset`                                                                           |
| **镜像备份**          | 每次备份都是独立目录 `mirror/<jobId>/`，**不会自动清理**。建议：只留最近 7 份日备、4 份周备，其余手工删；删之前确认新的那份能恢复（见 §3.8.4）       |
| 停用的归档计划        | 停用/删除计划不会清理任何历史数据，只是不再触发；想彻底停掉自动归档，逐个关掉 `enabled` 即可                                                         |

镜像备份的清理示例（NAS 目标，只保留最近 7 个目录）：

```bash
# 先看清要删什么，再删；把 NAS 路径换成你的目标挂载点
ls -1dt /mnt/nas/medihub/mirror/*/ | tail -n +8        # 列出要删的（第 8 个及更早）
ls -1dt /mnt/nas/medihub/mirror/*/ | tail -n +8 | xargs -r rm -rf
```

### 8.4 归档与备份任务失败排查

| 现象                                        | 原因                                                     | 处理                                                                                            |
| ------------------------------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 任务秒失败，`error` 提到存储/凭证           | S3 凭证或 bucket 错、目标被禁用                          | 系统管理 → 存储 → 对该目标点「测试」；修好后重试                                                |
| 失败，`EACCES` / `EPERM`                    | 目标目录不属于服务用户，或 NAS 只读挂载                  | `sudo -u www -H test -w <rootPath>`；修正属主或挂载参数                                         |
| 失败，`ENOSPC`                              | `/tmp` 或目标盘满                                        | `df -h /tmp`；降低分片大小、清理临时文件                                                        |
| 失败，内存被 OOM 杀掉（进程重启、任务消失） | 分片太大导致峰值内存过高                                 | 把分片降到 50–200 MB；给服务加 `max_memory_restart` / swap                                      |
| 失败，`SQLITE_BUSY`                         | 打包/快照期间大量写库与备份撞车                          | 别在备份/导出高峰跑归档；把计划错开到凌晨                                                       |
| 一直 `running` 超过一天                     | 极大量素材或网络极慢                                     | 看 `ps aux \| grep archive`、目标侧写入速率；必要时按 §8.3 清理并降低单次量（把截止日期往前挪） |
| 列表里看不到任务                            | `root` 未选科室（列表按科室过滤）                        | 顶部「科室」下拉先选一个科室                                                                    |
| **计划到点没跑**，`last_error` 提示体积超限 | 目标是 `local` 驱动，且本次待归档体积 ≥ 200 MB（§3.7.3） | 把计划目标改成 NAS/S3；或改小 `before_days` 分批                                                |
| 计划到点没跑，`last_error` 是别的错         | 目标不可写、凭证失效、无素材可归档                       | 按上一行同类错误处理；处理完等下一周期，或手工补跑一次                                          |
| 计划的下次运行时间是空的                    | 计划被停用（`enabled=0`），或 `next_run_at` 还没算出来   | 打开启用开关；必要时重启服务让它重新计算                                                        |
| 镜像失败，`VACUUM INTO` 报错                | 磁盘满、库被长时间锁、或目标不可写                       | 先看 `df -h`，再看 `error`；`VACUUM INTO` 需要一个能放下**整个库**的临时空间                    |
| 镜像 `ready` 但体积异常小                   | 只备份了数据库、没勾「同时复制素材文件」                 | 属正常（库本身只有几 MB–几百 MB）；需要素材副本请重新发起并勾选                                 |
| 镜像一直 `running`                          | 勾选了「同时复制素材文件」，正在复制全量素材             | 大库耗时以小时计；看目标侧写入速率与 `byte_size` 增长                                           |

### 8.5 日常监控

```bash
# 磁盘（阈值 30%）
df -h /data/medihub/storage /tmp

# 最近的归档任务
sqlite3 /data/medihub/local.db \
  "select id, status, asset_count, printf('%.2f GB', byte_size/1073741824.0), chunk_count,
          datetime(created_at/1000,'unixepoch','localtime')
   from archive_job order by created_at desc limit 10;"

# 归档总量
sqlite3 /data/medihub/local.db \
  "select printf('%.2f GB', coalesce(sum(byte_size),0)/1073741824.0) from asset where archived_at is not null;"

# 定时计划健康度：谁没跑成功
sqlite3 /data/medihub/local.db \
  "select id, enabled, frequency,
          datetime(next_run_at/1000,'unixepoch','localtime') as next_run,
          coalesce(last_error,'-') as last_error
   from archive_schedule order by next_run_at;"

# 镜像备份最近的几次
sqlite3 /data/medihub/local.db \
  "select id, status, include_assets, asset_count,
          printf('%.2f GB', byte_size/1073741824.0),
          datetime(created_at/1000,'unixepoch','localtime')
   from mirror_job order by created_at desc limit 10;"
```

建议把这三件事做成提醒：**磁盘剩余 < 30%**、**`archive_job` / `mirror_job` 出现 `failed`**、
**`archive_schedule.last_error` 非空或 `next_run_at` 已过期**（1Panel 计划任务 + 脚本，
或直接看 [DEPLOY-1PANEL.md §12.3](./DEPLOY-1PANEL.md#123-挂到-1panel-计划任务) 的计划任务通知）。

## 9. 限制与注意事项

1. **按上传时间筛选**：归档用 `asset.created_at`（上传到系统的时间），不是 `captured_at`（拍摄时间）。
   补传的老照片虽然拍摄于 2019 年，但只要今年上传，就不在「截止 2024 年」的归档范围内。
2. **一个任务最多 5000 条素材**。超出的部分不会被处理——需要按截止日期分批建任务。
3. **截止日期按 UTC 零点解析**：选 `2024-10-01` = 北京时间 `2024-10-01 08:00` 之前的素材。
4. **归档后素材在站点里不可预览**（勾了删源时），但记录仍在、仍参与搜索与统计元数据。
5. **额度在归档完成（`ready`）后释放**；任务 `running` 期间那些素材仍占额度。
6. **「删除服务器源文件」不可逆**（分片里有一份副本，但站点里打不开原文件）。勾选前确认
   归档包已上传成功、且目标可靠。
7. **勾错了没删源，事后没有「补删」按钮**：已归档的素材会被后续任务排除，想彻底清盘只能
   在存储侧手工删文件（额度已经释放，删文件不影响额度，但能真正腾出磁盘）。
8. **下载归档片要求 `root` / `dept_admin`**；`member` 与 `individual` 会被 403。
9. **归档不影响导出**：导出照样生成 ZIP，但源文件已删的素材只有元数据，`manifest.json` 里
   `included: false`，`README.md` 的计数也只算实际包含的文件。
10. **归档不迁移存储目标**：归档包写到任务创建时选的目标；历史素材仍留在原目标里（除非删源）。
11. **前端没有「已归档」徽标**：目前只能靠「能否预览」或后台字段判断（§4.1）。
12. **归档 ≠ 合规留存**：归档只解决容量，不替代审计与留存期管理；删分片前先确认院规。
13. **临时目录与内存**：分片先落 `/tmp` 再整体读入内存，`/tmp` 空间与进程内存都要能容下**一片**。
14. **定时计划只负责「发起」**：它每分钟检查一次并创建普通归档任务，**不会重试失败**、也不会
    因为上次失败而跳过下个周期；排查看 `last_error`（§3.7.4）。
15. **本地/NAS 目标的计划有 200 MB 上限**：本次待归档体积 ≥ 200 MB 时计划不执行（§3.7.3），
    这是防自动任务把服务器盘写满的闸门，不是 bug。大批量自动归档请把目标设为 S3/NAS 独立盘。
16. **一个计划一次最多仍受 5000 条素材限制**（与手工归档同一条查询），素材极大的科室要缩短
    `before_days` 让每轮量变小。
17. **镜像备份只备份数据库（+ 可选素材）**：`.env`、`STORAGE_ROOT` 的结构本身、`.updates/`
    不在范围内；恢复后仍需把素材文件放回正确位置（§3.8.4）。
18. **镜像「同时复制素材文件」是全量**：每次都是一份完整的素材副本，不增量、不自动清理旧备份；
    空间规划必须按「份数 × 素材总量」来算。
19. **镜像只有 `root` 能用**：`dept_admin` 与普通成员看不到入口，也不能通过接口触发
    （接口层同样按 root 校验）。
20. **镜像不能省磁盘**：它的目的是「数据还在」，与归档的方向相反；用镜像去缓解磁盘紧张只会更糟。

| `存储磁盘剩余空间不足：剩余 …，本次需要 …，并需预留 512MB` | 507 | 目标磁盘不够                           |

### 10.2 数据表与字段

| 表 / 字段                                   | 说明                                                                                                                                                                                                                                                                              |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `organization.quota_bytes`                  | 科室上限（字节，可空 = 不限）                                                                                                                                                                                                                                                     |
| `app_setting` 的 `storage.globalQuotaBytes` | 全站上限（字节的字符串，记录不存在 = 不限；设成 `0` 等于禁止上传）                                                                                                                                                                                                                |
| `asset.byte_size`                           | 单素材字节数，配额的唯一口径                                                                                                                                                                                                                                                      |
| `asset.archived_at` / `asset.archive_id`    | 归档时间与所属任务；任一非空即视为已归档（不计额度、不可再次打包）                                                                                                                                                                                                                |
| `archive_job`                               | 任务：`status`(`pending`/`running`/`ready`/`failed`)、`before_at`、`chunk_bytes`、`delete_source`、`asset_count`、`byte_size`、`chunk_count`、`chunks`(JSON: `index`/`key`/`size`)、`storage_target_id`、`error`                                                                  |
| `archive_schedule`                          | 定时计划：`enabled`、`frequency`(`daily`/`weekly`/`monthly`)、`hour`(0–23 本地整点)、`weekday`(1=周一…7=周日)、`day_of_month`(1–28)、`before_days`(默认 730)、`chunk_bytes`(默认 200 MB)、`target_id`、`delete_source`、`last_run_at`、`next_run_at`、`last_job_id`、`last_error` |
| `mirror_job`                                | 镜像备份：`status`(`pending`/`running`/`ready`/`failed`)、`include_assets`、`target_id`、`storage_prefix`、`db_key`、`manifest_key`、`asset_count`、`byte_size`、`error`、`completed_at`；`organization_id` 可为空（全站）                                                        |
| 分片路径                                    | `<存储目标内>` `archive/<jobId>/chunk-001.zip`（序号 3 位、从 1 开始）                                                                                                                                                                                                            |
| 镜像路径                                    | `<存储目标内>` `mirror/<jobId>/medihub.sqlite`（+ `manifest`，勾选时另有素材副本）                                                                                                                                                                                                |
